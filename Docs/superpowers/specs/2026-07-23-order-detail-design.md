# Детальная страница заказа — дизайн-решение

**Дата:** 2026-07-23
**Ветка:** `feature/prototype`
**Кабинеты:** `manager-web` (полная карточка), `client-portal` (клиентская проекция)
**Статус:** Реализовано

---

## Проблема

На дашборде менеджера (`manager-web`) таблица «Все заказы за сегодня» и канбан-карточки
выглядели кликабельными, но никуда не вели: роут `/orders/[id]` в кабинете менеджера
отсутствовал. Демонстрация упиралась в тупик — клиент кликает на заказ и ничего не происходит.

В `client-portal` карточка заказа существовала, но была тонкой: «Сводка» из семи полей
и заглушка «Документы». Она не показывала ни ход работы, ни согласование макета, ни оплату.

Отдельная проблема — данных для карточки в моках не было вовсе. Типы `OrderItem` и
`OrderHistoryEntry` были объявлены в `@uniprint/types`, но ни фикстур, ни handler'ов
под них не существовало.

## Решение

### Компоновка

**`manager-web /orders/[id]`** — двухколоночный экран для 1280–1440px:

```
[ ← Все заказы ]
Заголовок: название · UNI-2026-XXXXX · статус · тип · «просрочен»   [Счёт PDF] [Сменить статус]
┌──────────────────────────────────────────────────────────────────────────┐
│ Степпер статус-машины типа заказа (BR-07)                                │
│ [панель смены статуса — раскрывается по кнопке]                          │
└──────────────────────────────────────────────────────────────────────────┘
┌───────────────────────────────────────────────┐ ┌──────────────────────┐
│ Обзор · Производство · Экономика · Док. · Ист.│ │ Клиент               │
│                                               │ │ Ответственные        │
│ содержимое активной вкладки                   │ │ Деньги               │
│                                               │ │ Сроки                │
│                                               │ │ Доставка             │
└───────────────────────────────────────────────┘ └──────────────────────┘
```

Правая колонка `sticky` и не меняется при переключении вкладок — на демо экран
никогда не выглядит пустым, а ключевой контекст (кто клиент, сколько денег, когда срок)
всегда перед глазами.

Вкладки:

| Вкладка | Содержимое | Правила в UI |
| --- | --- | --- |
| Обзор | Позиции заказа с итогом, карточка макета | BR-04, BR-11 |
| Производство | Маршрут операций с исполнителями и временем, списанные материалы по партиям, карточка брака | BR-10, BR-01, BR-09, BR-03, BR-17, BR-23 |
| Экономика | KPI выручка / себестоимость / маржа / рентабельность, структура себестоимости план→факт | BR-18, BR-32 |
| Документы | Счёт, договор, акт, ТТН со статусом готовности | BR-25 |
| История | Timeline статус-переходов + форма комментария | BR-20, BR-13 |

**`client-portal /orders/[id]`** — тот же заказ клиентским взглядом:

- Укрупнённый степпер (4–6 стадий вместо 11 статусов) — клиенту не нужна внутренняя кухня
- Карточка макета с действиями «Согласовать» / «Отправить на доработку» — главное действие клиента
- Что заказано, документы, ход работы
- Сайдбар: оплата, получение, плашка BR-32

### Разграничение доступа (BR-32)

Ключевое решение: **клиентская проекция строится на стороне API, а не прячется в UI**.
`GET /api/orders/:id/detail?scope=client` возвращает другой тип — `OrderClientDetail`,
из которого удалены себестоимость, `managerId`/`designerId`, списания материалов,
внутренние комментарии и `driverUserId` доставки. UI физически не получает того,
что не должен показать.

Это проверяется юнит-тестом, который сериализует проекцию и ищет запрещённые ключи.
Тест поймал реальную утечку на этапе разработки: `driverUserId` водителя оставался
в блоке доставки.

### Данные

Детальная карточка **не хранится отдельной фикстурой, а выводится из самого заказа**
(`buildOrderDetail`). Причины:

1. Карточка есть у любого заказа, включая созданные через `POST /api/orders` во время демо
   (иначе golden-path «создать заказ → открыть его» упирался бы в 404).
2. Вывод детерминированный — никакого `Math.random()`, поэтому e2e-тесты стабильны.
3. Фикстуры остаются чистыми: 14 заказов, а не 14 заказов + 60 связанных сущностей.

Мутируемая часть (смена статуса, комментарии, решение клиента по макету) живёт в
`packages/mocks/src/store/order-store.ts` и накладывается поверх вывода. История
«материализуется» при первой мутации: до неё выводится из статуса, после — ведётся явно.
Без этого смена статуса давала бы дубль записи (одну выведенную, одну добавленную).

### Статус-машины (BR-07)

Три типа заказа — три разных маршрута, и это видно на экране:

- `cex` — лид → замер → дизайн → проверка макета → согласование → очередь → производство → контроль → готов → выдан → закрыт
- `office` — то же без замера
- `goods` — лид → очередь → контроль комплектности → готов → выдан → закрыт

Смена статуса разрешена только на следующий шаг своего маршрута (плюс «брак» из
производства и «отмена» откуда угодно). Попытка перепрыгнуть возвращает `409` с
объяснением — правило enforce'ится в API, а не только скрытием пунктов в списке.

## Новые компоненты `packages/ui`

| Компонент | Назначение |
| --- | --- |
| `Amount` | Денежная сумма единым начертанием (Fraunces + ₽). Убирает россыпь инлайн-стилей `fontFamily: var(--font-display)` по страницам |
| `FieldList` | Пары «подпись / значение» в карточках сущностей |
| `StatusStepper` | Маршрут статус-машины лентой: пройдено / текущий / впереди |
| `Timeline` | Журнал событий сущности |

`KanbanCard` получил проп `href` — карточки на канбане стали кликабельными.
`ORDER_STATUS_LABELS` вынесен из `order-status-badge` в экспорт: один словарь названий
статусов на бейджи, степпер и список выбора.

## Что осталось за рамками

- Загрузка макета и превью — реальные файлы в S3 (BR-33), в прототипе плейсхолдер
- Онлайн-оплата — кнопка выключена, провайдер эквайринга не выбран (🔴 Q5)
- Скачивание PDF — кнопка есть, генерация появится с backend (BR-25)
- Редактирование позиций заказа — не входило в задачу
- Storybook-стори для новых компонентов — Storybook в репозитории пока не настроен
